1. Project Overview
1.1 Concept
SENTINEL is a consumer-grade, plug-and-play network security appliance powered by an agentic AI system. It sits inline between a home ISP router and the internal network switch, acting as a transparent Layer 2 bridge — giving it full visibility into all home network traffic without requiring any reconfiguration of existing devices or the ISP router.
The system autonomously detects threats, profiles every IoT device, deploys deception technologies (honeypots and honeytokens), and enforces firewall rules in real time — entirely on the edge device with no mandatory cloud dependency.
1.2 Objectives
Design an agentic AI-powered IoT security system protecting home users from cyber attacks
Implement autonomous threat detection using LSTM Autoencoder + Isolation Forest
Deploy deception technologies: virtual honeypots (Cowrie, OpenCanary) and honeytokens
Build real-time automated response with eBPF/XDP + nftables firewall engine
Create a consumer-friendly plug-and-play security appliance (Raspberry Pi 5)
Deliver a unified real-time risk dashboard for all home IoT devices
Use Gemma 4 E4B LLM for on-device MITRE ATT&amp;CK TTP classification

2. Development Approach — PC First, Pi Later
2.1 Strategy
Build, test, and validate the entire SENTINEL software stack on a personal laptop or PC first. Only buy the Raspberry Pi 5 hardware after the software is fully working. This is standard embedded security development practice and the codebase is designed to be 99% identical across both environments.
2.2 What Runs Identically on PC and Pi
AI engine — LSTM, Isolation Forest, Gemma 4 via Ollama — runs on any 64-bit Linux/macOS/WSL2
Next.js dashboard — identical on both environments
All Docker containers: Cowrie, OpenCanary, Redis, Loki, Elasticsearch
FastAPI backend, threat intel pipeline, SQLite device registry
nftables firewall rules — same syntax on PC Linux and Pi OS Lite
LangGraph agent orchestration — pure Python, no hardware dependency
2.3 PC Workarounds (Temporary During Development)
Packet capture: use libpcap on local Wi-Fi interface instead of a two-NIC bridge
Monitor mode: TP-Link TL-WN722N v1 (~800 INR) gives full home network visibility without being the gateway
Firewall enforcement: iptables/nftables on loopback — functionally identical code to the Pi bridge setup
Honeypot redirect: DNAT rules on localhost — same nftables syntax, just a different target interface
2.4 Pi Porting Checklist (When Software Is Ready)
Add two-NIC bridge config via a single netplan YAML file
Recompile llama.cpp for ARM64 — one command, roughly 15 minutes on Pi 5
Docker containers pull ARM64 images automatically — no changes to Compose file
Swap Gemma 4 E4B for E2B in Ollama — same API, smaller model
All Python/Node application code stays 100% identical
Hardware budget: 
Raspberry Pi 5 (8GB) approx 6,000-7,000 INR. Buy only after software demo is working end-to-end on PC. TP-Link TL-WN722N for monitor mode during development: ~800 INR.

3.3 Layer-by-Layer Engineering Detail
Layer 1 — Network Capture &amp; Packet Engine
Uses libpcap and AF_PACKET sockets for raw traffic capture. nDPI handles deep packet inspection for 300+ protocols, producing per-flow metadata: source/destination IP, protocol, TLS SNI, HTTP User-Agents, DNS queries, and application-layer protocol identification.
Layer 2 — Device Discovery &amp; Risk Profiler Agent
Combines passive and active fingerprinting. Passive: ARP broadcasts, mDNS (.local names), SSDP/UPnP descriptions, DHCP hostname options — identifies 80%+ of devices without sending a single packet. Active (weekly, low-noise): Nmap OS detection and service version scan.
MAC-to-vendor via IEEE OUI database. CVE scoring via NVD API — vendor and product strings from fingerprinting are queried to pull CVSS scores. Results stored in SQLite device registry.
Schema: device_id, mac, ip, vendor, os_guess, firmware_version, open_ports[], cve_list[], risk_score, last_seen, baseline_model_path
Layer 3 — Agentic AI Engine (Three Agents via LangGraph)
Three specialised agents run concurrently, communicating via Redis pub/sub, orchestrated by LangGraph.
Anomaly Detector Agent: LSTM Autoencoder trained on per-device traffic baselines (bytes/sec, packets/sec, top destination IPs, DNS query rate, connection attempt rate). Isolation Forest for cold-start (new devices with no baseline). Reconstruction error above learned threshold fires anomaly event to Redis.
Threat Classifier Agent: Gemma 4 E4B via Ollama. Receives anomaly events from Redis, maps them to MITRE ATT&amp;CK for ICS/IoT using native function calling, outputs structured JSON: {tactic, technique_id, confidence, severity, summary, recommended_action}. Also checks IoCs against local STIX threat intel store.
Response Planner Agent: YAML-defined policy tree. Severity 9-10 = immediate quarantine + dashboard alert. Severity 6-8 = redirect to honeypot + alert. Severity 1-5 = log + passive monitor. Calls firewall engine via internal FastAPI REST endpoints.
Layer 4 — Deception Layer
Multi-tier deception stack running as isolated Docker containers on the same appliance. Each honeypot gets its own virtual IP via macvlan — they appear as separate physical devices to the network.
Cowrie: SSH/Telnet honeypot — logs all attacker commands, credentials, and session behaviour
OpenCanary: Multi-service honeypot — emulates HTTP, SMB, FTP, MySQL, Redis services
Custom UPnP honeypot (U-POT style): serves fake device description XML files impersonating smart bulbs and IP cameras
SDN-style traffic steering: when attacker is detected, nftables DNAT rules redirect their traffic to the appropriate honeypot without them knowing
Honeytokens: fake AWS keys, API tokens, and credentials planted in UPnP responses, fake HTTP headers, and exposed Samba shares — trigger out-of-band alerts via Canarytokens when used
Cowrie session logs fed to Threat Classifier Agent for real-time TTP identification from attacker commands
Research note: 
The honeypot selection is dynamic, not static. The Response Planner agent decides which honeypot to redirect each attacker to based on their classified TTP — SSH probe goes to Cowrie, HTTP scan goes to OpenCanary. This AI-driven deception coordination is a novel contribution.
Layer 5 — Firewall &amp; Response Engine
eBPF/XDP programs attached to network interfaces — sub-millisecond packet decisions, blocks known-bad IPs at line rate before they touch the kernel network stack
nftables for stateful rules: port blocking, connection rate limiting, DNAT for honeypot redirect
Python rule manager daemon subscribes to Redis and translates agent decisions into live nftables commands
VLAN micro-segmentation: pushes VLAN assignments via SNMP on managed switches to isolate device classes from each other
Auto-quarantine: DHCP starvation + static ARP injection isolates a compromised device without any router config change
Security gate: 
Any destructive action (quarantine, firewall block) triggered by the LLM requires explicit dashboard confirmation for severity 8+. This prevents prompt injection attacks from silently taking network actions.

4.2 Gemma 4 — Why It Is the Right Choice
Gemma 4 was released April 2, 2026 by Google DeepMind under the Apache 2.0 license. It is the recommended LLM for SENTINEL for the following reasons:
Native function calling — agents call block_ip(), redirect_to_honeypot(), send_alert() as first-class LLM tools, not fragile prompt hacks
128K context window on E2B/E4B — feed full packet logs, CVE context, and MITRE descriptions in a single prompt
Apache 2.0 license — publish the full SENTINEL system including the model with zero licensing restrictions
Confirmed Pi 5 compatibility — E2B runs at 7.6 tokens/sec on Raspberry Pi 5 with 8GB RAM
Multimodal capability — future extension: feed IP camera frames for physical intrusion detection without any model change

9. Novel Research Contributions
Three angles give SENTINEL genuine academic value beyond a standard implementation project:
9.1 On-Device LLM TTP Classification at Under 10 Watts
Running a quantized 4B LLM (Gemma 4 E4B) for real-time MITRE ATT&amp;CK TTP classification entirely on a Raspberry Pi 5 at under 10W of power is a novel result. Very little published work has demonstrated LLM-based threat classification on a single-board computer without cloud connectivity. The confirmed 7.6 tokens/sec on Pi 5 (E2B) makes this practically viable and directly reproducible by other researchers.
9.2 AI-Driven Dynamic Honeypot Coordination
Honeypot selection and traffic steering in SENTINEL is dynamic — the Response Planner agent makes per-attacker decisions about which honeypot to redirect traffic to, based on the LLM-classified TTP. An SSH probe goes to Cowrie; an HTTP scan goes to OpenCanary; a UPnP probe goes to the camera emulator. This AI-driven deception coordination at the edge is an original combination not present in existing consumer-grade tools.
9.3 Consumer-Grade Threat Attribution on a Sub-100 Dollar Device
Combining passive fingerprinting, per-device LSTM behavior baselining, and deception telemetry to build attacker profiles on a 75 USD device is a publishable result — especially when benchmarked against existing tools like Snort and Suricata on the same traffic traces. This comparison can form the core of the evaluation chapter.
